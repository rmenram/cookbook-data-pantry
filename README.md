# Overview

As a developer, I wanted to use this project to learn how to perform CRUD operations using Python and Firebase, a cloud NoSQL database. I built a decoupled architecture. I split my menus, user prompts, and database connection logic so the database engine can be reused across different projects later on.

I wrote a python-based backend that integrates with a remote Google Cloud Firestore database. The system uses two files: `smm_db_core.py` handles the actual cloud connection and CRUD loops, while `test_db_driver.py` acts as a testing console. To run the program, you launch the driver script in your terminal to open the command-line menu. From there, you can pick options 1 through 5 to add mock data, search your collections using keywords, update document titles, or trigger a full cascading delete.

My purpose for writing this software was to build an organized storage system for text chunks. You can think of this program as a digital data pantry. When text strings come in, this backend shelves them, categorizes them, and lets you pull them back down using keyword searches.

# Cloud Database

For this project, I chose Google Cloud Firestore as my NoSQL database engine. Firestore is a serverless document store that uses a flexible, schemaless collection-and-document layout.

To handle relational data in a NoSQL environment, I built a one-to-many relationship using two separate collections linked by reference IDs:

- **`cookbooks` (Parent Collection)**: Tracks the main source entries. Each document uses a readable string ID (like `test-bible`) and stores the `title` (string), `file_path` (string), and `added_at` (timestamp).
- **`recipe_chunks` (Child Collection)**: Holds individual text fragments. Every document gets a unique random ID generated by the cloud and contains a `cookbook_id` (the key that links the fragment straight back to its parent book), `page_number` (integer), `text_content` (the plaintext fragment string), and `added_at` (timestamp).
